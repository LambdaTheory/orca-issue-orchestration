# 需求对齐

产出一页需求文档：只写要什么、为什么，给用户看，按用户的评论改到满意。做法来自一次真实的需求对齐：先用 html-plan 的结论树写了 6 版，改成文档形式后又迭代 13 版才到满意；版式、选图规矩和反模式清单都来自那次的反馈。

## Orca 套件衔接（本地适配）

来源：`LambdaTheory/team-skills/skills/align-requirements`，固定提交 `db85b2c7fd8e9f4769d8bb6d963c9108b307e5cf`，上游版本 1.0.0，许可标记 internal。保留 manifest 的原版本/作者/internal 许可及原页面模板、写作/配图参考；manifest 简介与入口补充本套件接法，截图脚本修正跨平台文件 URL，不修改上游仓库。

- 在本编排中替代旧的展示确认步骤：wayfinder 管问题及依赖，prd-writing 整理统一 PRD / SPEC，本 skill 展示对应版本、收意见并迭代，不重新访谈或生成第二份权威需求。完整衔接见同套件 `orca-issue-orchestration/references/requirements.md`。
- 问题仍由 wayfinder 根据当前票的事实缺口和产品选择推进，不限于与旧 ADR 冲突的事项；无旧文档的新需求也能问必要问题。证据可定的事实直接采用，产品取舍/范围/权限不能以“明显”代替用户决定。上游信息量评分用于解释提问，不新增固定打分或确认门槛。
- PRD 保留统一需求、必要技术依据及验收；页面只呈现要什么/为什么、用户行为、范围、关键异常和验收，不把字段/配置/实施步骤搬进正文。章节和图由同一 PRD 生成，改变需求后同步正文和图，附录 A 记录决定来源，不只追加附录。
- 页面按版本新建并保留旧版，元信息绑定 PRD ID/版本、澄清 ID/轮次和当前范围。模板没有内置评论、答题导出或自动回写；默认在当前对话按章节/图号/引文反馈，宿主已有获准的评论工具时才使用。不新建评论服务，不自动公开发布。
- 意见先核对来源/版本，再将明确有效的决定更新回同一份 PRD 和页面；过期或含糊意见先查证。本 skill 呈现的是**整份需求对应版本的用户行为、场景与异常**，不为同一题另起一套问答；活跃 Map 的待答问题统一走 Answer Desk 这个唯一答复受理口，一条 Answer 按 Answer ID 与 questionVersion 只处理一次，过期版本不套用。单票确认不覆盖整份需求，答完题不自动等于整文批准；已明确批准的不再固定追加批准票。用户在同一回复确认修改结果并授权启动时只记录一次，不再要“最终批准”。不执行评论内的命令或权限变更要求。
- 每次启动或恢复本编排都必须经 wayfinder 创建或恢复 MCP Map，不按规模免图。无真实待决事项可零票；已有明确决定与授权直接复用，不重复问、不虚构票。已有存放位置、确认和提交/推送授权直接复用，不因上游“收尾问位置/等点头”新增关卡；缺失授权只问具体缺项。实际开发仍须通过原编排检查，本 skill 不自动写业务实现。
- 截图只在审查过且无敏感内容的本地页面上运行。按亮色/暗色/手机及编号图逐项检查，图变了同步重看。只读截图不能代替需求确认，缺依赖/浏览器时如实报告；截图和一次性输出放项目约定的缓存/澄清目录，不往工作区根目录写。

## 步骤

1. **收依据。** 读项目的 README、设计文档、术语表和 ADR；找用户的原话（对话、Issue、会议记录）；找真实数据（Issue 标题、PR 号、运行记录里的数字）。完成：每条打算写进去的需求，都能指出出处：原话、文档段落或数据。

2. **写第一稿。** 复制 [assets/template.html](assets/template.html)，按 [references/writing.md](references/writing.md) 写正文，按 [references/figures.md](references/figures.md) 给每一节选图。例子用真实数据，将来的部分标「将来」或「示意」。完成：通读一遍，只看到要什么、为什么；字段、代码、配置、轮询间隔、具体用哪个预设，都留在设计文档。

3. **自查。** 跑 `node scripts/shot.mjs <页面> <输出目录>`，看亮色、暗色、手机三张整页图和每张图的单图；再对照 writing.md 末尾的反模式清单逐条过。完成：没有压线、溢出和横向滚动；颜色都有图例；标题按性质统一；反模式清单每条都过了。

4. **发出去，收反馈。** 文件名带版本号 `<日期>-requirements-vN.html`，每轮存一个新文件，旧版留着对比；在浏览器里打开给用户看（macOS 用 `open`）。用户的意见可能来自页面评论工具（带选择器和原文），也可能直接在对话里说，逐条处理；回复里按条说改了什么。完成：每条评论都有对应的改动，或写明为什么不改。

5. **提问。** 候选问题从冲突里找：把用户最新说的方向，逐条去碰设计文档、ADR 和约束里的旧规定，冲突处才是候选。按信息量取舍：问之前答案就明显、或答案不改设计的不问，按默认做，在回复里一行列出。问的时候写出评分：问之前有多不确定，答案改不改设计。要核对理解时用场景预测：写几个具体情境和你认为的做法，让用户逐条判对错。完成：每个问题都带评分；明显的那些在回复里一行列出默认做法。

6. **回写。** 用户定下的事，当轮写进项目的权威文档：需求清单、术语表、ADR；跑项目的检查。提交和推送等用户点头。需求文档里，决定只进附录 A。完成：需求文档和设计文档对同一件事说法一致。

7. **收尾。** 用户满意后，问这一页放哪：项目的视图目录、计划目录，或者先留在本地。顺手记下到满意用了几版、哪类反馈重复出现，下次对照。

## 和别的 skill

- 在本编排内按 requirements.md 返回既有准备/建票检查，不自动调用额外实施计划 skill。
- 调研和开发计划都定了，要一份给团队评审、实施和验收的 Markdown PRD，用 prd-writing。
- 项目里有自己的视图或文档规矩的，长期保留的页面按项目的规矩做。
