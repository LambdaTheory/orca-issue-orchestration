# 写需求文档

## 需求和方案怎么分

需求写要什么、为什么、对谁、边界在哪、必须满足什么性质。方案写怎么做：判断的具体依据（看提交包含关系还是看标签）、批处理方式（每天一页验收）、轮询间隔、字段、配置、代码、某个项目具体用哪个预设、命中风险时怎么切换。

判别问题：换一种实现，用户的要求还满足吗？满足，这一条就是方案，写进设计文档。

## 版式

照 assets/template.html：标题、副标题、元信息（状态、版本、日期、负责人、怎么做见哪）、摘要、左侧目录、编号章节、编号图和图说明、附录 A 决定记录、附录 B 术语、页脚。

- 定下的事只进附录 A，正文保持干净。
- 等用户定的事用「待你定」标注，写出倾向和理由；定了就删掉标注，记进附录 A。
- 编号的要求清单留在设计文档，用来核对设计有没有覆盖到需求；需求文档里不重复。
- 图号按出现顺序连续编号；删图、加图后重排一遍。

## 标题

- 一级标题用名词，例如交付、流程、运行保障、范围。
- 讲怎么运作的节，二级标题写「如何……」，例如「如何创建或修改一个流程」。
- 讲必须满足的性质的节，二级标题写陈述句，直接说出这条保障，例如「一个 Issue 跑几周，也不用人守着」。
- 两类放在不同的一级标题下，并在那一节开头用一句话说明这一节是什么。
- 每个标题回答使用者的一个问题，避免只描述机制。

## 句子和用词

- 中文短句，主动语态，同一个东西始终用同一个词，以项目的术语表为准。
- 用冒号或分句代替破折号；用正向陈述代替否定句。
- 用真实数据做例子：真实的 Issue 标题、PR 号、数字。将来的部分标「将来」或「示意」。
- 只写用户提过的需求；自己想到的，放进回复里问。

## 反模式清单

来自那次真实对齐里用户的反馈。每次发出去之前逐条过一遍。

| 反模式 | 用户当时的话 |
|---|---|
| 暴露字段、代码、配置 | 可以不用暴露细节（比如字段那些东西） |
| 方案混进需求 | 又是【混淆了需求和方案】 |
| 加用户没要的东西 | 好像没有这个需求？虽然有吸引力，但是别额外加东西吧 |
| 正文里满是「已定」 | 这种【已定】去掉吧 |
| 把基础规则写成定数 | 没有什么「只打扰一次」之类的，打扰次数少只是个基础规则 |
| 颜色没有图例 | 这种绿底底是什么意思？ |
| 图的类型不适合这条信息 | 可能是因为你这个图的类型就不适合展示这个信息。我觉得你可以新增一个图 |
| 用现有实例堆矩阵 | 你不用执着于把现在的项目、阶段、预设都覆盖进来，这个是后面方案设计的事情 |
| 标题形式不统一，性质混在一起 | 几个章节的标题不统一；这两个性质不一样哦 |
| 只改文字，图没跟着改 | 你这个改动是不是只修改了文字？从图上也看不出来 |
| 问答案明显的问题 | 有些问题答案比较明显……这种问题提出来，我觉得没有多大的意义 |
