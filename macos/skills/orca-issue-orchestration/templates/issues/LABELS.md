# 标签使用规范

仓库有四个**固定标签**，另有一个按任务动态命名的**任务标签**。

- 固定标签：`enhancement` / `bug` / `needs-user` / `gate`，语义固定，长期存在。
- 任务标签：`<task-name>`，每个任务一个，名字不固定，但必须是简洁英文小写 kebab-case；用于圈定“哪些票属于当前任务范围”。


| 标签 | 类别 | 允许出现的位置 | 含义 |
|---|---|---|---|
| `enhancement` | 类型（永久） | 仅 `[实现]` | 实现票 |
| `bug` | 类型（永久） | 仅 `[缺陷]` | 缺陷票 |
| `needs-user` | 状态（临时） | 仅用户节点 | 当前依赖已满足、下一步确实在等用户处理 |
| `gate` | 状态（临时） | 仅用户节点 | 当前仍阻塞至少一个下游票或交付动作（合并/发布/真实数据操作） |
| `<task-name>` | 范围（按任务） | 本任务的所有票 | 该票属于哪个任务；用于与历史/其他任务的票区分 |


## 任务标签

任务标签不是固定值，每个任务在开工时确定一个简洁英文名。

- **命名**：纯任务名，简洁英文小写 kebab-case，2–4 个单词、不超过 30 字符。例：`dynamic-models-csrf`、`csrf-fix`、`auth-refactor`。不加任何前缀，不用中文、空格、冒号或斜杠；与四个固定标签重名时换一个更具体的名字。
- **创建**：需求确认、拆票完成后，建票前创建；同一任务恢复时先查同名标签，复用而不重复创建。颜色统一用紫色 `#5319e7`，description 写任务全名与开始日期。
- **应用**：本任务创建的每一张票都加，包括实现票、缺陷票、用户验收/决定票，以及开发中新增的补票；纳入本任务范围的既有票也补加。每张票只带一个任务标签。
- **保留**：任务是历史范围标记，票关闭后**不摘除**。任务结束后标签继续保留，便于按 `label:"dynamic-models-csrf"` 回看整套票。
- **不用于状态**：任务标签与 `needs-user`/`gate` 正交；不要用它表示进度、优先级或当前待办。

## 核心原则

**`needs-user` 标签视图 = 当前真正等你处理的票。**

被其他 Issue 阻塞、依赖未满足、或已经验收完成的票，都不打这个标签。

- 不在建票时给所有用户节点预先打 `needs-user`。
- 同一依赖链上只标最前面的那一张；默认同一时刻只有一张 `needs-user`。
- 只有互不阻塞的并行分支才可能同时出现多张，并且每张都要能独立执行。
- 实现票/缺陷票永远不带 `needs-user` 或 `gate`。需要用户动作时另开用户节点票。

## 判定流程

```
这张票属于哪个任务？→ 先加 `<task-name>`

这张票要写代码吗？
├─ 是 → 是修故障吗？
│        ├─ 是 → bug
│        └─ 否 → enhancement
└─ 否 → 它现在能执行吗（Blocked by 全部满足）？
         ├─ 否 → 不打 needs-user / gate
         └─ 是 → 下一步在等用户吗？
                  ├─ 否 → 不打 needs-user
                  └─ 是 → needs-user
                           └─ 仍阻塞下游/交付？→ 再加 gate
```

## 生命周期

0. **任务开工**
   - 创建或复用 `<task-name>`；
   - 之后本任务创建的每张票都先加这个标签。
1. **建票**
   - 所有类型都加 `<task-name>`
   - `[实现]` → `enhancement`
   - `[缺陷]` → `bug`
   - `[用户验收]` / `[用户决定]` → 暂不打标签；若建票时依赖已满足、马上要用户处理，可直接加 `needs-user`。
2. **成为当前前沿（依赖全部满足）**
   - 加 `needs-user`；
   - 若它仍阻塞下游票或交付动作，同时加 `gate`；
   - assign 用户，并发一条以「需要你处理」开头的评论。
3. **等待用户期间**
   - 保持 `needs-user`；
   - 被阻塞的后继节点只带任务标签，不带 `needs-user` / `gate`，直到依赖满足。
4. **用户已答复**
   - 用户动作完成、没有新的待答项：移除 `needs-user`；
   - 若仍需协调者执行用户授权的事项，或仍阻塞下游/交付：保留 `gate`，直到真正解锁；
   - 答复不完整或验收不通过：保留 `needs-user`，并说明还缺什么。
5. **关闭**
   - 同时移除 `needs-user` 和 `gate`；
   - 类型标签 `enhancement` / `bug` 保留，作为历史分类。

## 同步与自检

每次唤醒、收到用户答复、阶段变化或合并结果时，先核对标签再继续：

- [ ] 本任务所有票都带同一个 `<task-name>`，且没有混入其他任务标签
- [ ] 本任务新建的补票也已补上任务标签
- [ ] 所有 `needs-user` 票的 `Blocked by` 都已满足
- [ ] 没有“已验收/已决定但还没移除 `needs-user`”的票
- [ ] 没有实现票/缺陷票带 `needs-user` 或 `gate`
- [ ] 每张 `needs-user` 票都有 assignee 和「需要你处理」评论
- [ ] 已关闭的票不带任何状态标签
- [ ] 标题以 `#<票号>` 开头，编号与实际票号一致，类型前缀与标签一致

## 常见错误

- 建票时给所有用户节点预打 `needs-user`，标签视图里全是“等你处理”，实际只有一张可执行。
- 用户已答复/已验收却不移除 `needs-user`，标签失去“当前待办”的含义。
- 给被其他 Issue 阻塞的用户节点打 `needs-user`，把依赖问题误报成用户问题。
- 给实现票/缺陷票加 `needs-user` 或 `gate`，混淆类型与状态。
- 用户节点关闭后仍保留 `needs-user` / `gate`。
- 建票时漏加任务标签，按任务名筛选时看不到完整范围。
- 同一任务恢复时重复创建同名或近似名的任务标签。
- 一张票带多个任务标签，或把任务标签当状态标签使用。
