# Issue 模板集

本目录按**票据类型**拆分，是 `templates/issue.md`（单页通用底稿）的展开版。
每份模板都可直接复制为 `issue.md` 正文，用 `gh issue create --body-file` 建票。

## 四类票据

> 本任务所有票统一加范围标签 `<task-name>`；下表只列固定标签。

| 类型 | 标题（编号在最前） | 用途 | 是否写代码 | 建票时的标签 |
|---|---|---|---|---|
| 实现票 | `#<n> [实现]` | 一个可独立验收的行为切片（功能、改造、迁移） | 由 Orca worker 实现 | `enhancement` |
| 缺陷票 | `#<n> [缺陷]` | 定位并修掉一个有证据的故障 | 由 Orca worker 修复 | `bug` |
| 用户验收节点 | `#<n> [用户验收]` | 必须由用户实际操作确认的体验/最终验收 | 不写代码 | 依赖未满足时**不打 `needs-user`**；成为当前前沿后加 `needs-user`，阻塞下游/交付时再加 `gate` |
| 用户决定节点 | `#<n> [用户决定]` | 必须由用户拍板的数据、权限、对外动作或取舍 | 不在本票实现 | 同上 |

## 标签使用规范

固定标签只有四个：`enhancement`（实现票）、`bug`（缺陷票）、`needs-user`（当前在等用户）、`gate`（当前阻塞下游/交付）。

另有一个按任务动态命名的范围标签 `<task-name>`（简洁英文小写 kebab-case），本任务所有票统一加，用于和历史/其他任务的票区分；票关闭后不摘除。

**关键规则：`needs-user` 是状态标签，不是类型标签。** 只有依赖已满足、下一步确实在等用户的节点才打；被阻塞、已验收、已关闭的票都不打。

完整的判定流程、生命周期和自检清单见 [LABELS.md](LABELS.md)。

标题格式：`#<n> [类型] <主题>`，编号在最前。`<n>` 用建票后 GitHub 返回的真实编号回填，不使用临时序号。

标题示例（来自实际项目）：

- `#12 [实现] 模型下拉只保留可生成图像的模型（方案 A）`
- `#13 [缺陷] Agent 规划「计划不是有效 JSON」`
- `#14 [用户验收] 切换上游模型并自动切换协议`
- `#15 [用户决定] 非 images/responses 协议模型在下拉中如何呈现`
- `#16 [用户决定] 授权合并 PR #16（#15 方案 A）`

## 通用写作规则

1. **一票一个纵向切片。** 能独立验收的行为，不按文件/模块拆票，也不构造假依赖。
2. **确认依据必须不可变。** 引用 SPEC 版本、需求快照或澄清记录；worker 读不到的内容内联进正文，不让可变文档悄悄改需求。
3. **范围写两面。** “要做”之外必须写“不做”，并写清权限、隐私、数据边界。
4. **验收必须可观测。** 写行为、命令、环境、成功标准；没有现成测试就明确要建立的验证。不默认全量测试或 build。
5. **依赖用真实编号。** 先创建全部票，再用 `gh issue edit --body-file` 回填 `Blocked by: #n`；临时编号不算数。代码依赖在 PR 实际合并后才满足。
6. **交付措辞决定关闭方式。** 合并即满足全部条件才用 `Closes #n`；仍有验收、其他 PR 或用户决定时用 `Refs #n`。默认交付 PR，不自动合并。
7. **实现/修复必须派 Orca worker。** 协调者只查证、建票、派发、验收，不写业务实现、业务测试或修复代码。
8. **用户节点独立成票。** 依赖满足、成为当前前沿后才加 `needs-user`（阻塞下游/交付时再加 `gate`），assign 已核实账号，并发一条以「需要你处理」开头的评论；被阻塞的用户节点先不带标签，只在对话里问不算。
9. **本地状态不自动同步 GitHub。** 用户答复、阶段变化、合并结果当轮同步；同步成功后才声称完成。
10. **关闭条件。** 实现/缺陷票：关联 PR 全部 MERGED、验收满足、无未决用户节点。用户节点：用户明确确认后由协调者写结论并关闭；否决、取消、手工关闭都不等于通过。

## 需要用户反馈时

以下情况一律开**独立的用户节点票**，不塞进实现票正文：

- 数据确认：需要用户判断当标准
- 不可逆 / 对外动作：改真实数据、扩大权限、真实投递、授权合并
- 体验验收：用户天天要用的界面
- 最终验收：上线前

## 配套的派发说明

票据本身不承担 worker 指令。派发时另用同目录上一级的：

- `templates/dev.md`：开发任务说明
- `templates/fix.md`：评审意见修复说明
- `templates/review.md`：独立评审说明

## 常见错误

- 标题不带类型前缀，四类票混在一起无法分辨。
- 标题编号不在最前，或回填的编号与实际票号不一致；建票后未重新回读标题。
- 把“待用户决定”写进实现票的“范围”，导致 worker 替用户做产品决定。
- `Closes` 用早，代码合并把还没验收的用户节点一起关掉。
- 验收写成“功能正常”“测试通过”，没有命令、环境或可观察结果。
- 依赖填临时编号或凭感觉建依赖，导致并行顺序错误。
- 缺陷票先猜原因再改代码，没有复现步骤和直接证据。
- 建票时给所有用户节点预打 `needs-user`，标签视图里全是“等你处理”，实际只有一张可执行。
- 用户已答复/已验收却不移除 `needs-user`，标签失去“当前待办”的含义。
- 给被其他 Issue 阻塞的用户节点打 `needs-user`，把依赖问题误报成用户问题。
- 给实现票/缺陷票加 `needs-user` 或 `gate`，混淆类型与状态。
- 建票时漏加 `<task-name>`，导致按任务筛选时看不到完整范围。
