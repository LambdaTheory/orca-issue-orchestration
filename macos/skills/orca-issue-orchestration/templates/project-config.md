# 项目编排配置

本模板供协调者初始化时填写，不是可直接执行的配置。已有事实直接填入并注明来源，只有缺失选择/冲突/授权才问用户；使用前替换占位符，可选不适用项写“不适用”。不写入密钥。

## 需求确认前置检查
- 仓库探查：<已完成/未完成；实际 Git 根目录或非 Git 目录；是否有项目内容>
- 已读取的内容与事实来源：<指引、需求/确认记录、相关代码、依赖与测试入口；空工作区写实际检查结果>
- 直接继承的事实与决定：<已有功能、技术栈、限制、验收依据；不再向用户确认>
- 仍缺失或冲突的信息：<查证后仍需用户决定的具体事项；没有则写无>
- 远端状态：<已有远端已核实/待需求确认后创建/尚未明确>
- 远端核查证据：<地址来源、真实 owner/name、访问状态；无本地 remote 不等于无远端，查询失败不等于不存在>
- 待新建计划：<归属、仓库名、可见性、创建授权原话或记录；已有仓库则不适用>
- 前置结论：<两项均通过才进入 html-plan；待新建计划明确可通过，无需先建库>

## 目标与工具
- 项目路径：<实际路径>
- GitHub 仓库与 remote：<已核实的 owner/name、URL、remote 名称及来源；未创建则注明待创建，不编造 URL>
- 远端创建结果：<需求确认后的创建/查重回执、真实 URL 与可见性；已有仓库则不适用>
- PR 目标分支及基准取得方式：<分支；如何核对最新基准>
- Orca repo 选择器与执行环境：<实际选择器；本地或已配置环境>
- 开发 Agent：<实际可用的 Orca agent ID>
- 独立评审 Agent：<实际可用 ID；候选可轮换，每轮仅一名，不叠加完整 code-review 或两路子评审>
- 普通子代理：仅只读查证/分析；若明确用作唯一独立评审，不再叠加 Orca 评审，不承担实现或修复
- 最大并发：1（已有明确约定优先）；同一模型服务的开发、修复、评审和原生子代理共用额度
- 启动核实：<实际 Agent、配置模型、向导就绪与启动回执；structured/terminal 类型及可用读取入口>
- 临时故障：503/断流先对账、取回已完成报告；按 Orca 恢复指引，同一任务最多自动重试 2 次，不重复派发；未知状态不判死亡，无变化配置错误不重试
- 等待：当前工作范围内有未关闭 Issue 就保持一个 GitHub watcher（webhook 或已配置的 gh 回退），开发评审/PR交付/长期待验收都不能停挂。先 init、gh 校对当前状态，再 wait；处理并 ack 后仍有开放票就重挂。开发评审另挂 Orca 事件/健康检查，仅用户待答时只停 worker 等待，不停 GitHub 通道；空等待不周期唤醒模型
- 监听范围与检查点：<本次需求对应票号清单，含新增用户节点；watcher mode/真实后台 handle/status。全部票查证 CLOSED 且批次处理完才停止，用户明确暂停或接管交接除外；连接中断记 recovering/blocked，不称仍在监听>
- worker 健康检查：默认间隔 60 秒、done/idle 未结算宽限 120 秒、无可见进展阈值 900 秒；对应 orch_wait.py 的 --health-interval / --idle-grace / --stale-after。健康异常才唤醒模型，告警先核实，不自动判死或重派；仅用户待答时不启动该检查
- Skill 安装目录：<本次加载的 SKILL.md 所在绝对目录；可由 ORCA_ISSUE_SKILL_DIR 覆盖，与项目路径分开>
- Python 解释器：<实际 Python 3 命令或绝对路径；可由 ORCA_ISSUE_PYTHON 覆盖；Windows 默认 python，macOS 默认 python3，调用带 -X utf8>
- implement Skill 路径：<已核实可达的绝对路径，写入开发任务说明；同套件通常位于 Skill 安装目录的同级 implement/SKILL.md>
- Skill 可达性：<worker 如何读取共享套件；自包含任务说明来源>

## 需求与验收
- 项目指引、SPEC、tracker 路径：<沿用已有位置>
- 确认记录与需求版本：<现有记录位置或澄清记录位置>
- 依赖/环境建立命令：<从仓库核实的命令；不需要则不适用>
- 测试、构建与功能验收：<明确约定的命令及适用条件；无约定则只做本次必要验证，不默认全量测试/build；无现成测试则由实现票建立最小验证>
- 证据复用：<命令、结果、环境、适用范围、SHA 与证据位置；同 SHA 且环境/范围未变的有效结果复用，新改动/失败/未解决疑点才扩大验证>
- PR 检查：<必须通过的检查；缺失时如何补齐/处理>
- E2E：<按任务判断的适用性；需要时的执行方式>

## 边界与权限
- 允许修改与禁止区域：<项目实际约束>
- 私有数据、凭据、网络、端口：<实际边界；未使用则不适用>
- GitHub 用户节点接收账号：<核实的账号>
- Issue 状态同步：<沿用 tracker 的状态/标签/负责人约定；无则维护一条协调者进度评论。收到回复当轮同步，问题答清移除 needs-user，仍有待答项则保留>
- 完成关闭：<用户节点明确通过且验收满足后由协调者关票；实现票关联 PR 全部合并且验收/用户节点完成后关闭。PR 核实为 MERGED 即已结束，不额外 pr close>
- 同步记录：<评论 ID/链接、实际 issue_state/pr_state、同步回执；失败记 sync_pending，恢复先对账，不重复评论>
- 授权记录及范围：<本地配置/Git/远端建库（归属、名称、可见性）/Orca注册/建票评论/状态标签与指派同步/完成后关票/推送开PR/派发等；已有授权引用，各动作分别明确，不写“全部允许”>
- 交付：默认 PR，不自动合并；只有明确授权才协调者合并
- 评审间保留已结算开发终端：<用户授权记录；未授权时遵循 Orca 释放/后续新终端机制>
- 通知：默认当前对话及授权范围内 Issue 评论；外部机器人未配置不阻断普通任务。提示用户以新增评论回复；编辑旧评论的通知可见但不等于自动批准
- 暂停与恢复：<本项目必须交用户决定的事项；权限/工具失败保留现场并从原步骤续接>
