# 操作细则

从 SKILL.md 的阶段导航进入，只读取当前相关小节。下列模板与脚本路径均以已解析的 `SKILL_DIR` 为基准；`S` / `W` 等命令定义见[命令参考](commands.md)。

## 基于文件的状态（协调者不靠记忆）

编排时间长、对话会被压缩，协调者也可能换人。所有状态写在文件里，协调者每一步都是“读状态 → 处理一个事件 → 写回状态”，不依赖对话上下文。

- 位置：`<repo>/.orchestration/<run_id>/`（自动加入 `.gitignore`，只在本机）。`state.json` 是当前事实：每个 Issue 的阶段（blocked / ready / dev / review / fix / verify / merged / user_gate / closed）、PR、worktree、终端 handle、dispatch、依赖；等用户回答的问题；所有协调者必须遵守的规则；备忘。`events.md` 是只追加的事件日志，写“做了什么、为什么”。
- 工具：`scripts/orch_state.py --repo <repo> --run <run_id> <cmd>`，命令有 `init`、`show`、`set <issue> k=v ... --why`、`ask`、`answer`、`rule`、`note`、`event`、`reviewer`（每次选择一名评审，候选可轮换）。默认 `show` 只读未完成任务关键字段、全部待答问题与用户约定、最近 3 条备注；`show --issue <n>` 查单票全部字段（含已完成票），`show --full` 显式查全部任务与备注，`--events N` 按需查历史。历史保留在文件里，不因摘要截断而删除。`active_issues` 是任务数，不是运行 Agent 数；已交付 PR 标为待合并，不计执行中。
- 每次被唤醒（收到真实事件或用户提问）：先 `show`，需要细节再查单票；只有状态变化才 `set` / `event` / `note` 写回，不记重复等待。每票收口用 `checkpoint` 保存短结论，并记录实际 SHA、测试/评审证据位置及 `next_action`；`worker_state`、`blocker` 有变化才更新，不另建记忆系统。需要继续等事件时按等待策略挂后台。
- 用户在对话中做的决定，当场写成 `rule`（并同步 SPEC / 票据）；向用户提的问题写成 `ask`，得到回答后 `answer`。
- worker 的长报告不贴进对话：结论写入 `state.json`，原文留在 PR 评论或 worker 输出里，需要时再读。
- 接手：新协调者（任何 Agent）执行 `orca orchestration run-use --id <run_id>` 绑定 Run，读本 skill、项目编排配置和 `show`，按需查 `show --issue <n>` / `--events N` 即可继续；不需要旧对话。交接前确认没有处于“已提问未回复”的 worker。

## 每个 Issue 的流水线

```
开发（<开发Agent>，新 worktree，从最新 <目标分支> 开分支）→ 必要测试与本地提交 → Standards / Spec 自查 → 按授权推送、开 PR → worker_done
→ 一次独立评审（Orca <评审Agent>，同时核对需求与正确性）→ 评审报告与 worker_done
→ 有必须修改项才交给 Orca 开发 worker 修复、做必要回归验证 → worker_done → 同一评审流程只复查修改与回归点
→ 无必须修改项：协调者核对对应 SHA 的有效证据、验收与可合并状态，必要时补验证
→ 按配置交付 PR；仅获合并授权时 gh pr merge --squash → 结算释放并记录检查点 → 继续已授权任务或结束
```

依赖任务在被依赖的 PR 合并后才从新 <目标分支> 开工，不叠分支。并发上限是项目参数（默认 1）；同一模型服务默认只运行一个执行或评审 Agent，开发、修复、Orca 评审与原生子代理共用额度，不为评审另开并行通道。空闲保留终端不算正在执行，评审候选列表不代表评审路数；协调者仅处理事件，不轮询倒计时。已有明确并发约定优先。

评审前由开发者同步最新 <目标分支>、解决冲突并完成必要测试与推送，再固定待审 HEAD；评审期间不修改共享 worktree。一名独立评审同时核对需求、正确性、相关异常路径与集成行为，不额外启动完整 `/code-review` 或两路子评审，不让评审者再派生评审 Agent。

协调者为独立评审提供固定基点 SHA、待审 HEAD SHA、Issue / SPEC 正文或路径、规范文件及评审范围，并写入 Issue 状态的 `review_base`、`review_head`；每轮结论关联实际 SHA。首轮审完整任务变更；修复轮保存 `previous_review_head`，确认它是新 HEAD 的祖先后审 `git diff <previous_review_head> <review_head>`，只复查修改与相关回归点。若历史已重写，原增量证据失效，再重新固定基点确定评审范围。工作区不干净或评审期间 HEAD 变化时，不能复用原结论。最终交付核对完整需求的覆盖证据，不把增量评审当成全部需求验收。

## 评审力度与节奏

- **只为「必须修改」开修复轮**：必须修改是有具体证据的功能错误、错误状态或未完成的已确认需求，包括会造成真实数据丢失、越权或违反隐私边界的错误；不扩成泛化安全审计。非阻断建议记录在当前评审报告即可，不阻断交付，不自动创建清理 Issue 或派发额外任务。
- **批准的多步计划一口气推进**：用户批准一个多步计划（例如「按建议顺序做」）后，每步合并完直接开下一步，不再逐步询问。只有遇到需要用户拍板的设计取舍才停。
- **默认一次独立评审**：由一名评审完成需求与正确性核对；发现必须修改项也不自动增加第二路。项目明确约定的评审要求仍遵守，不临时叠加评审层。
- **按证据做必要验证**：用户或项目明确约定的测试照旧；否则不默认全量测试或 build，只验证本次范围及回归点。同一 SHA 且验证环境、命令与适用范围未变时复用有效结果，报告注明命令、结果、SHA 和证据位置。只有新改动、新失败或未解决疑点才扩大验证；缺失或失败的证据不能当作通过。

合并权限是项目参数：用户授权后，验收通过即由协调者合并，不再逐个等用户。未授权合并的默认 PR 交付模式，在最终 SHA 对应的验收、约定 PR 检查与可合并状态通过后记录 `stage=verify delivery=pr_delivered pr=<编号> delivery_sha=<SHA>`，报告交付而非已合并；已结算 worker 按授权保留或释放，worktree 保留待后续处理。不为交付额外索要合并权限，依赖该代码的任务仍等待实际合并。

## 任务说明

用 `templates/` 下的模板，填好再派发。必须自包含，并提前写清这些会被反复问到的点：

- 测试切入点遵守 Issue / SPEC 的明确约定；未指定时由开发者在任务范围内选择并记录，不逐个确认。涉及需求、接口契约或权限变化时用预置 ask 向协调者提问；这是 TDD 的编排例外，独立使用 TDD 仍须用户确认。
- 开发者先检查暂存、未暂存和未跟踪改动，再本地提交并按 Standards / Spec 两轴自查，不调用完整 /code-review、不派生子 Agent。必须修改项修复、测试、提交并复查通过后才推送；本地提交不等于验收。一次独立评审由协调者在 worker_done 后安排，并提供固定基点、待审 SHA、Issue / SPEC、规范和已有测试证据。
- 跨模块的值（处理方式代码、类别名等）一律引用已合并模块的常量，不复制字符串。
- 修改前先合并最新 <目标分支>；合并冲突由开发者解决。
- 测试环境（如 `.venv`）的建立命令。
- 隐私与数据边界：线上 Agent 不读私有数据；私有数据只读访问主 checkout 的路径。
- 带用户节点的 Issue：开发者只做到“工具可用、候选就绪”，不替用户确认；PR 写 `Refs #n` 而不是 `Closes #n`，避免代码合并提前关闭用户节点；用户明确确认且完成条件满足后，由协调者按下文同步并关闭，不要求用户手工关票。

## 处理 worker 的提问

- 范围问题按 SPEC 和最小改动原则直接答，不扩大范围；超出本任务的另开 Issue。
- 涉及产品规则、而 SPEC 没写的：不改变已确认需求、接口契约或权限的细节可先给保守默认，同时把问题单独交给用户；涉及这些边界的变化须先完成 ask 和用户决策，不以临时默认放行。其他不受影响的工作可以继续。
- 模型效果问题（本机模型判错）不靠调提示词凑通过：确定性测试必须过、不依赖实时模型输出；模型合格性归回放任务。
- 空心跳（`subject` 为 `alive`、正文为空）由 `orch_wait.py` 在壳里 ack，不要向用户汇报。心跳里如果写了进度，脚本会把整批交出来，再决定要不要说。

## 用户节点

到达节点时用项目约定的通知渠道和接收人通知用户，写清：要验收什么、在本机怎么打开（完整命令）、做完回复什么。消息里不放私有内容。用户负责作决定与确认验收；协调者负责收到回复后的状态同步和满足条件后的关闭，不把手工关票留给用户。提示用户以新增评论回复；恢复会话时重新读取待答 Issue 的评论内容与更新时间，不按评论数量判断回复是否已到。服务端投递 `issue_comment/edited` 时，webhook watcher 会报告旧评论的编辑事件，即使 `comment_id` 不变也须处理新的事件批次；编辑通知本身不等于新答复或自动批准，仍须读取正文及更新时间，对照原问题判断是否形成有效答复后再更新状态。本地消费者测试不证明线上服务已订阅并投递编辑事件；线上联调须在获准的测试 Issue 新增再编辑同一评论，核对两个事件批次及处理后的 ack，不能把模拟测试结果写成线上已验证。

### Issue / PR 可见状态同步与关闭

本地 `S set` / `S answer` 不会更新 GitHub。每次处理用户回复、阶段变化、验收或合并结果时，协调者须在本轮先同步远端可见状态，再继续派发或结束；不能只改 `state.json`。复用项目已授权的评论、标签/指派调整和关闭权限，初始化时一次说明这些动作；缺权限只问缺项，不再次确认需求，也不从建票授权推定合并授权。

1. **收到用户回复**：读取评论原文及对应问题/需求版本，记录评论 ID 或链接（编辑过的回复同时记录更新时间）、决定和剩余未答项。对话内的明确答复也须同步到关联 Issue。仅“收到”、部分答复或否决不是验收通过；共享账号时结合内容与已有协调者评论记录识别，不凭作者判断。相同答复已处理则不重复评论或操作。
2. **立即更新用户可见进度**：沿用 tracker 的状态字段/标签；没有时维护一条协调者自己的进度评论，写清当前阶段、已采纳答复、剩余阻断、关联 PR 和下一步，不覆盖用户正文或评论。仅在真实变化时更新。所有待用户问题已答清后移除 `needs-user`；仍有待答项则保留并列明。用户已回答但验收未通过时转为修复/处理中，不仍显示“等用户”，也不关闭。实际解除的阻断才移除，`gate` 类型标签不表示是否通过；指派按现有约定转回实际负责人，不编造账号、不为未配置 Projects 新建看板。
3. **用户节点关闭**：纯决策/验收节点在所需明确确认全部取得、该票验收全部满足时，由协调者写结论与依据，并关闭为 completed；含实现工作的票仍须同时满足实现与合并条件。否决、取消或手工关闭不等于通过，不能据此解锁下游。剩余决定未明确则继续保持开放。
4. **实现 Issue 关闭**：所有关联实现 PR 已合并到约定目标分支，验收满足且无未决用户节点后，核查 Issue 是否已自动关闭；仍开放则执行 `gh issue close <n> --repo <owner/name> --reason completed`，随后查询确认。`Closes #n` 只用于合并即满足该票全部完成条件的情形；仍需后续验收、其他 PR 或用户决定时用 `Refs #n`，避免提前关闭。不能依赖关键词必定生效，尤其目标并非默认分支时。仅 worker_done、评审通过或 PR 已交付未合并，不关闭实现票；无代码任务按其明确完成条件关闭。
5. **PR 合并收尾**：执行合并或收到外部合并通知后，用 `gh pr view <pr> --repo <owner/name> --json state,mergedAt,headRefOid` 核实。`state=MERGED` 且有合并时间表示 PR 已结束，不再执行 `gh pr close`；后者是未合并关闭，不能拿来代替合并。启用自动合并或进入合并队列不等于已合并，仍按待合并记录；`CLOSED` 但未合并则记录该结果、不解锁代码依赖。PR 交付后由用户合并的，在收到通知或下一次恢复时查询相关 PR 并补齐收尾，不为此恢复开发期的周期 watcher。
6. **同步成功才声称完成**：每次远端变更后查询 Issue 状态、标签及进度评论，核对 PR 结果并保存回执；记录 `issue_state`、`pr_state`、`last_user_comment`、`progress_comment_id` 等实际值。写入失败/结果未知时记录 `sync_pending` 和具体待办，报告“本地已处理，GitHub 尚未同步”，下一次先读取远端对账再补做，不重复刷评论或宣称已关票。代码已合并可记 `stage=merged`；全部完成条件及关票同步完成后记 `stage=closed`，另存 `gate_result=approved` 或实际结果以判断用户依赖，不能仅凭 closed 判定通过。

## 收尾

每个 PR 确认 `MERGED` 后：记录实际 PR 状态与 `stage=merged`，按上文同步关联 Issue，满足全部完成条件的关闭并核验，仍有验收/用户节点的保持开放并显示下一步；结算并释放剩余 Dispatch；确认没有活动 worker、未提交改动或未交付的提交，且测试证据、评审报告及产物已保存在 PR 或 worktree 外的持久位置后，执行 `orca terminal close --worktree <selector> --all`，再按当前 Orca 帮助归档并删除该 worktree。squash 合并不能只用提交祖先关系判断是否交付，须核对 PR 已合并的 head SHA 与本地 HEAD，并确认没有额外本地提交。任一检查失败、状态未知或清理失败时保留现场并记录阻断，不强制删除。

把依赖已满足的任务设为 ready、按依赖补满并发；没有可执行任务时如实告诉用户在等什么（哪个评审、哪个用户节点）。已授权交付完成后按 Orca `orchestration` 的完成要求报告结果、对应 SHA 与证据，保存每票短检查点并结束；仍待合并或用户验收的明确标注，不宣称已结算。安全释放已结算 worker，清理失败保留现场并单独报告，不因资源清理或非阻断建议继续扩实现任务。
