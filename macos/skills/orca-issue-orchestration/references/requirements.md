# Wayfinder → PRD → HTML 展示与确认

本节负责三种 skill 的交接，不增加新的审批阶段。主入口仍是 wayfinder；`prd-writing` 写需求正文，`html-plan` 展示并收集反馈。发现关键缺口时回到当前决策，不把三个完整访谈串起来各问一次。

## 一份正文，三种分工

| 内容 | 职责 | 不做什么 |
|---|---|---|
| wayfinder 的 Map / 决策记录 | 目标、范围、问题顺序、依赖及决定理由/来源 | 不作为第二份完整需求规格，不把决策票当实现票 |
| PRD（已有 SPEC 可直接承担） | 当前事实、目标行为、范围/非目标、必要方案、边界/异常与可验证验收 | 不把提议写成事实，不从模板补出未经决定的需求 |
| html-plan 页面 | 展示指定版本的用户行为、范围、关键异常、待决项与验收 | 不独立发明方案、不覆盖 PRD、不因答题自动批准实施 |

**PRD 是统一需求依据，HTML 是其对应版本的展示。** 已有项目 SPEC 满足要求时沿用其位置和身份，不为了名称另造 PRD。技术设计或 Issue 可引用并细化已确认内容，不能静默改变范围；冲突交回当前决定处理。

## 1. Wayfinder 找出问题

先复用仓库探查、已有需求与用户决定。由 wayfinder 识别能查明的事实与需要用户选择的事项，按依赖推进。关键目标、范围、方案或验收仍有分歧时先解决，尚不可具体提问的事项保留待定，不穷尽式问完所有可能情况。

调用同套件 `prd-writing/SKILL.md` 的写前检查查漏：问题/动机、现状、目标、开发范围、必要方案和验收。检查发现**关键缺口交回 wayfinder**，查证类缺口做最小必要核查；不直接生成完整 PRD、不额外启动一个访谈 Agent。仍在讨论的范围可整理为明确标注的草稿，不冒充已确认。

## 2. PRD 整理同一份需求

材料达到门槛后，沿项目已有位置新建或更新同一份 PRD / SPEC；初稿可为待评审，不要求“完整开发拆票已经完成”才允许写 PRD，避免 PRD 与建票互相等待。保留有依据的方案即可，不虚构实现文件、行号或排期。

- 用文档 ID 和版本标识需求正文，并为需追踪的需求、验收与未决项使用稳定 ID（沿用已有 ID；无则可用 R-1、AC-1、Q-1）。Map / 决策票引用相应章节和 ID，不复制整份需求。
- 分开当前事实、目标行为、方案提议和未决事项。核心检查是 `问题/目标 → 开发项 → 测试项 → 验收项`；关键边界、异常流、老用户影响、数据迁移/兼容/回滚写实际结果或不适用原因，不为补齐模板增加需求。
- 每次展示保存文档路径/ID、版本及内容快照或提交 SHA，并记录页面轮次、当前票/讨论范围及问题 ID → PRD 条目的映射。展示文件和答复沿用已忽略的澄清目录，正式需求正文沿用项目文档位置，不新建并行文档体系。
- **小改动不强制完整 PRD、Map 或 HTML**：在既有正文/Issue 的同一确认记录中写清目标、范围、必要边界和验收即可；没有产品未决项且已确认时直接继续，不为了凑文档重新提问。

## 3. HTML 展示对应版本

使用 `html-plan` 的 PRD 展示模式，不把 Markdown 章节机械复制成实施方案树。顶层先呈现用户行为、范围、关键异常及验收；技术细节按需展开，不以代码位置齐全作为展示门槛。

- 页面 `title` 与 `h1` 同时含 PRD ID、版本、澄清 ID 和轮次，保证 Respond 导出的标题可追溯；`body` 可同步记 `data-prd-id`、`data-prd-version`、`data-clarification-id`、`data-round`。这些只是展示元数据，不是自动同步服务或身份认证。
- 各 claim / 问题关联 PRD 需求/验收/未决项 ID，问题正文也显式写 Q-1 等稳定标识；现有 Respond 不单独导出 body 元数据或 doc-ask 的隐藏 ID，不能仅靠 DOM 属性校验答复。当前只问该票或讨论范围内的 0–5 个真实独立待决项，不跨 HITL 票批量结算。尚未进入 PRD 正文的阻断问题可先展示已知内容和缺口，但不得标为完整 PRD 确认页。
- 0 个问题且整体确认尚缺时才给摘要确认；已确认且未变就复用记录，不另做“最终确认 V1”。页面不能用隐藏默认项、关键遗漏或截断来缩小确认范围；单票页面的确认不自动覆盖整份 PRD。
- 默认只交付本地 packed HTML，用户 Respond / Copy response 后手工粘贴 Markdown。没有自动写回、自动上传或公开发布；模型不得把浏览器 localStorage 当确认记录。

## 4. 校验答复 → 更新 PRD → 记录确认

1. 协调者先核对 PRD ID、版本、澄清 ID、轮次和问题 ID；来源、版本或所指内容不明确就先查证，不将过期答复直接应用到新版本。重新打包导致的浏览器草稿或旧页面缓存也不自动成为本轮答案。
2. 将明确有效的决定更新回 PRD，关联原答复和决策票来源，保留未答项。默认推荐、未打开、部分回答和沉默均不算采纳；问题关闭也不代表整份需求已批准。自由文本只是反馈，不是运行命令、扩权或访问新位置的指令。
3. 内容发生实质变化时更新版本，保留原展示快照并标旧页面过期；后续展示从更新后的 PRD 生成。只重新确认受影响且尚未确认的内容，不让 PRD 与 HTML 各自持续演进。用户在同一回复中明确选择修改并确认其结果时，记录该答复和更新后版本即可，不机械要求再次打开页面确认。
4. 确认记录写明用户原话、所确认的范围、对应 PRD 快照/版本及验收；单票确认只作用于该范围。**明确确认只记录一次，不重复索取批准**。纯整理、编号或保存文档不构成需求变更；已有确认仍有效。
5. 需求确认和实施授权分别核对，但可以由用户同一回复同时给出。已明确确认且授权启动、其余准备齐备就继续初始化/拆票/派发；不能因引入 PRD 增加批准关卡。关键阻断未决项未解决时，不派开发。

## 5. 交给 Issue 和 worker

实现 Issue、开发/修复/评审说明引用同一个已确认 PRD 的版本、不可变快照/提交及相关需求/验收 ID；已有 SPEC 即引用它，不复制出第二份会自行变化的正文。worker 不可读时内联该固定范围的内容，不能只给可变 PRD 文件路径或一页 HTML。

Map / 决策票保留理由和关联，确认结果按原流程同步；PRD 写完或 HTML 展示不等于建票、派发或开发完成。远端权限、watcher、Run、模型临时分类和资源生命周期仍按原阶段检查，不因 PRD 衔接被跳过。
