# PRD Writing

把已完成的 Bug/需求调研结论和已完善的开发计划，整理成团队可评审、可执行、可验收的 Markdown 文档。默认结构和每章写法见 `references/team-prd-template.md`。

## Orca 套件衔接（本地适配）

来源：`LambdaTheory/team-skills` 的 `skills/prd-writing`，固定提交 `db85b2c7fd8e9f4769d8bb6d963c9108b307e5cf`，上游版本 1.1.0，许可标记为 internal；保留随附 manifest 和模板。本节优先说明编排内的接法，独立使用仍遵守下文材料门槛。

- **分工**：wayfinder 负责发现和推进待决问题；本 skill 负责写前检查、整理需求与验收；align-requirements 只展示对应版本的 PRD 并收集答复。完整交接见同套件 `orca-issue-orchestration/references/requirements.md`，不另开一轮访谈。
- **缺口返回**：可以先做材料评估，但目标、方案或范围仍有关键分歧时，只输出缺口清单和已有内容，不生成伪完整 PRD，不把未决项默认为推荐答案。需要产品决定的缺口交回 wayfinder；可查事实做最小核查，不重复扫描全部材料，也不强制派子代理。
- **统一依据**：沿用项目已有 PRD / SPEC 的文档位置，指定一份需求正文，修订同一份文档，不每轮另建互相竞争的 PRD。已有 SPEC 满足约定时直接复用其作为 PRD，不强制改名或搬家。Wayfinder MCP 地图的 Ticket / Settlement 保留决定的理由与来源，PRD 记录 Map/Ticket 标题+ID、Answer ID、Settlement 与需求/验收 ID 的关联并引用其结果；HTML 不是另一份需求依据。
- **版本与回写**：PRD 带文档 ID、版本和需求/验收 ID；页面绑定同一 PRD 版本和当前讨论范围。协调者先校验答复来源和版本，再将有效决定更新回 PRD 并记录来源；保留已展示快照，不覆盖旧答复。内容改变才更新版本；纯整理不重新索取批准。
- **确认与授权分开**：答题、浏览页面或默认推荐不等于整体确认，答完一张题也不自动等于整文批准；用户在同一回复中明确确认范围/验收并授权启动时，记录一次就继续，已明确批准的不再固定追加批准票。继续实施须同时满足：相关 Map 票全部 settle 且无阻断未决项、PRD 同步完成、范围确认、实施授权。关键未决项未解决不得进入开发；不把“PRD 写完”当需求已批准或开发已完成。
- **统一流程**：每次启动或恢复本编排都必须经 wayfinder 创建或恢复 MCP Map，不按规模免图。无真实待决事项可零票，已有明确决定与授权直接复用，不重复问、不虚构票。更新同一需求正文的目标、范围、必要边界和验收；原模板只提供排版结构；即使没有独立章节，也须在对应章节覆盖下文必写检查，不能以模板未列为由漏掉边界或异常。复杂需求保留异常流、老用户影响、兼容/迁移/回滚和验收映射；不适用写原因，不为了凑章节虚构方案。技术方案只细化到能判断范围和验收，不以尚未实现的文件行号、全部实现票或排期已经齐备作为写 PRD 的先决条件。
- **输出路径**：按项目已有文档约定写入；无约定时提出最小落点，未获确认前仅在已忽略的澄清目录保存草稿。只更新授权范围内的 PRD，不覆盖参考模板，不向上游仓库回写或自动公开发布。

## 适用与不适用

适用：

- Bug 已完成复现、根因和影响范围调研，需要同步团队。
- 需求已完成现状分析、方案决策和开发拆解，需要形成 PRD。
- 已有 PRD 草稿，需要按规范查漏补缺。
- 需要把零散聊天、调研报告、开发计划合并为一份正式文档。

不适用（应先补齐或改用其他方式，不要编造完整 PRD）：

- 调研尚未开始，或根因/目标方案/开发范围仍有关键分歧。
- 用户只需要一句结论、简单 TODO 或提交说明。
- 纯视觉设计稿或营销文案。

## 核心边界

1. 以整理和同步为主，不以重新调研为主；已有结论足够时不重复扫描代码、Git 或外部文档。
2. 不擅自改变已确定的方案、范围和优先级；认为有风险时写入“待确认”，不静默改写。
3. 不把推测写成事实，不把“调研完成”写成“开发完成”。
4. 只使用有证据的结论；无法确认的内容统一进入“待确认事项”。

## 输入

优先从当前会话、用户文件和既有调研结果收集：调研对象、当前现象、已确认结论（根因/链路/影响/边界）、目标行为、开发计划（改动点/模块/阶段/依赖/风险）、测试与验收方案、可选参考 Markdown 与输出路径。可用来源包括代码调研结论、Codegraph 结果、分析文档、技术方案、Git/DB/日志证据摘要、用户业务决策、外部契约结论。

## 工作流

### 第一步（必做）：判断调用模式并做写前规范评估

写 PRD 正文前，先判断调用模式，再做一次规范符合性评估；评估未通过时先补齐，不得直接输出完整 PRD。

| 调用模式 | 判定 | 处理 |
|---|---|---|
| 从头写 PRD | 只有调研结论、开发计划或零散材料，无成稿 | 一开始就注入本 Skill 规范，评估材料后再生成 |
| 查漏补缺 | 已有 Agent 整理的 PRD 或用户提供的草稿 | 把本 Skill 当审查规范，逐项评估缺口，补齐后输出修订版 |

**材料门槛**（缺关键项先补，不缺关键项才动笔）：问题/需求、当前行为、根因或动机、目标行为、开发范围、开发方案、验收方式。只缺负责人/编号/排期等非关键项时用 `—`、`待定`、`待排期`。

**评估必须覆盖**：

- 是否区分当前事实、业务目标、开发方案、待确认事项。
- 是否明确目标、非目标、功能范围边界和关键边界情况处理。
- 是否覆盖异常流的用户可见结果、系统记录和恢复方式。
- 若改已有功能，是否说明老用户路径、历史配置、默认值、权限、已创建数据和进行中流程的影响。
- 是否评估历史数据、数据迁移、补偿脚本、灰度、回滚和兼容策略。
- 每个关键开发项、边界情况、异常流、兼容性场景是否有对应测试或验收项。

**评估发现缺失/矛盾/证据不足时**：先列缺口，不包装成已确认；对需要源码、数据、日志、历史记录或外部契约确认的问题，派发对应 subagent 或做最小必要调研；补齐后更新 PRD，仍无法确认的写入“待确认事项”并注明需要谁确认什么。

### 第二步：汇总材料，不重新发散调研

按 `为什么做 / 当前是什么 / 要变成什么 / 怎么做 / 有什么风险 / 怎么证明 / 当前进度` 压缩已有材料。材料冲突时区分事实与决定：当前行为以已验证源码/数据证据为准，目标行为与范围按用户最新决定更新；二者不同不表示事实被覆盖。开发计划不得覆盖已确认范围；无法消解的冲突列入“待确认事项”。

全程必须区分四类内容，禁止混写当前行为/目标行为、已实现/计划能力、外部真实返回/本地期望文案、源码事实/高可信推断：

| 类型 | 写法 |
|---|---|
| 当前事实 | “当前代码/系统……” |
| 业务目标 | “修复后/上线后应……” |
| 开发方案 | “计划新增/修改……” |
| 待确认 | “需要业务/外部账号/生产数据确认……” |

### 第三步：按结构生成正文

默认章节（参考文档章节不同时以参考为准；每章详细写法见 `references/team-prd-template.md`）：

```text
文档标题 · 文档信息表
1. 背景（业务在做什么 / 出了什么问题或新需求 / 已确认原因 / 为何现在做）
2. 目标与非目标（目标可衡量；非目标控制范围）
3. 现状分析（短链路图 + 断点表 或 现状限制表，用业务语言）
4. 方案设计（以已定开发计划为准，不擅自重排；每个方案对应一个现状问题或目标）
5. 边界情况处理、异常流与兼容性评估（见下，必写）
6. 接口与数据契约（涉及接口/异步/外部系统/复杂状态时）
7. 实施状态与测试验收
8. 上线与验证顺序（适用时）
9. 待确认事项（存在时）
```

保持映射闭环：`问题/目标 → 开发项 → 测试项 → 验收项`；缺环时补齐或标记待确认。

### 第四步：边界情况处理、异常流与兼容性评估（必写）

不得只写正常主路径。这里的“边界”不只是需求范围/非目标，更包括边界情况的处理说明：系统遇到边界值、空值、重复、并发、状态临界点、权限变化、历史数据等情况时如何表现、记录、恢复。逐项检查并补齐：

| 评估项 | 必须说明 |
|---|---|
| 功能范围边界 | 覆盖哪些用户/入口/数据/状态/渠道；哪些不处理 |
| 边界情况处理 | 空值、缺省值、极值、超长、重复提交、并发、状态临界、部分成功/失败的处理结果 |
| 异常流 | 参数错误、权限不足、业务不满足、外部失败、超时、限流、重试失败的用户可见表现和系统记录 |
| 老用户影响 | 改已有功能时：老用户路径、历史配置、默认值、权限、已创建数据、进行中流程是否受影响 |
| 数据迁移 | 是否需迁移历史数据/补默认值/补索引/修脏数据/补偿脚本；不需要也写明原因 |
| 向后兼容 | 老客户端/旧入口/旧数据结构/旧配置是否可用；不兼容则说明原因、替代路径和用户影响 |
| 灰度与回滚 | 是否需开关/灰度/白名单/回滚；失败时如何恢复旧行为或止损 |
| 验收补充 | 每个边界情况/异常流/兼容性场景都有对应测试或验收项 |

信息不足以判断某项时，不省略也不编造，明确写“待确认”。

涉及接口/外部系统时，错误至少区分：参数错误、本地业务校验、外部业务拒绝、外部临时异常、系统技术异常。外部业务拒绝要保存并展示真实外部原因，不得统一包装成“系统异常”，也不得在本地硬编码文案冒充外部响应。

### 第五步：写实施状态与测试验收

状态只用有证据的结论，并写明是“调研完成”还是“开发完成”：`已完成 / 待实施 / 待排期 / 待确认`。

测试计划覆盖：正常主路径、Bug 复现路径、空值/边界值/非法参数、外部业务拒绝、外部临时异常、技术异常、异步状态、重试与幂等、多渠道/多对象部分成功、关闭新功能后的兼容路径、老用户路径、历史数据与迁移结果。验收用表格 `序号 | 验收项 | 验收方法 | 预期结果`，并从用户视角和系统证据两侧验证。

### 第六步：生成并复核

首次生成独立 Markdown，不覆盖参考模板；已有需求正文则按授权更新同一份 PRD / SPEC，保存所需历史快照，不另建第二份权威文档。重新通读并按下方“复核清单”核对，最后返回文件路径、版本和一句用途说明。

## 复核清单（生成前逐项确认）

- 已完成写前规范评估，并说明是“从头写”还是“查漏补缺”；缺口已调研补齐或列入待确认。
- 文档信息表完整，章节编号连续，区分现状/目标/方案/状态。
- 目标与非目标清楚；现状问题、开发项、测试项、验收项一一对应。
- 已写关键边界情况的处理结果（不只是需求范围）；已列关键异常流的用户可见结果和系统记录。
- 改已有功能时，已说明老用户路径、历史配置、默认值、权限、已创建数据和进行中流程影响。
- 已评估数据迁移、补偿脚本、默认值兼容、灰度或回滚方案。
- 边界情况、异常流、兼容性场景均有对应测试或验收项。
- 实施状态准确（区分调研完成/开发完成），未把推断写成事实，未改动用户已定方案。
- 团队成员不看原始调研材料即可独立理解并执行。

任一关键项不满足时，先补充材料、派发调研或标记待确认，不要伪造完整度。

## 输出风格

面向产品、研发、测试、项目管理共同阅读；业务语言优先，类名/行号仅作必要证据；多用短段落、表格和流程图；结论明确，不用“可能大概也许”，不确定内容统一进“待确认”；文档可直接进入团队评审，不依赖当前会话上下文。
