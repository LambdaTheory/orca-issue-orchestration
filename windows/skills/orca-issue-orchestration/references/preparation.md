# 准备工作

从 SKILL.md 的阶段导航进入，只读取当前相关小节。下列模板与脚本路径均以已解析的 `SKILL_DIR` 为基准。

## 首次使用：发现事实并引导初始化

先读工作区已有指引、需求/SPEC、确认记录、Git remote/分支、依赖清单与脚本、测试、Issue、issue-tracker 文档、编排配置和已有 Run 状态。确定项目路径后立即执行 `C start`，早于需求探查和建 Run；启动时间只记录一次，恢复时复用。只读执行适用检查（如 `git status`、`git remote -v`、`gh auth status`、`orca status --json`、`orca repo list --json`，其他接口先查帮助），不输出凭据、不把隔壁项目的设置当成本项目事实。

把所需信息分为以下四类，并在配置草案或澄清记录中标注来源：
- **已知事实**：仓库内容、工具回执等可核实信息直接采用，不问用户“是否正确”。可能过期就自行重新核查。
- **既有决定**：当前范围内有效的项目约定和用户选择直接继承，不因为尚未授权实施就重问一遍。
- **缺失或冲突**：先查相关文件、历史/回执；仍无法解决且会影响任务才说明冲突并问用户。
- **新决策或授权**：只询问真正需要用户决定的行为、范围和权限，不把事实包装成选择题。

### html-plan 前必须完成的两项检查

这两项是协调者的事实核查与必要决策，不是要求用户再批准一次需求。未完成前，不调用 html-plan、不生成需求选择题，也不进入其他形式的需求访谈；已有有效检查记录且相关事实未变时直接复用。

1. **主动探查仓库内容**：先查看工作区目录与适用的 Git 状态，再阅读项目指引、README、已有需求/SPEC、确认记录、相关代码入口、依赖及测试脚本、tracker 和编排配置。按本次任务范围提取已有功能、技术栈、限制、测试入口和既有决定，记录文件/命令来源；不只列目录就算完成，也不越过私有数据或凭据边界。后续问题逐项与已读内容对照：可自行查明的信息直接采用，不向用户确认“仓库里是不是这样”；仅询问查证后仍缺失、冲突或真正新增的选择。空工作区也须实际检查并记录“无现有项目内容”；只有 `.git` 或系统元数据不算已有业务内容，但仍须核查 Git 元数据，不以“无代码”推断无 remote。
2. **明确远端去向**：检查本工作区 Git 根目录、remote、配置和用户已给定的仓库地址，不能误用父目录或其他项目的 remote。已有明确远端时，只读核实真实 `owner/name`、URL、访问状态及其与当前项目的对应关系，直接沿用，不让用户重复确认地址；多个 remote 且用途不明、地址冲突或权限无法核实时只询问具体缺项。没有本地 remote 不等于没有远端仓库：先核查已有配置/地址，必要时问使用哪个已有仓库还是新建；登录失败、网络异常或无权访问不能当作仓库不存在。
   - **已有仓库**：记录核实后的目标和连接方式；本地为空时先在授权范围内取得并阅读远端已有项目内容，再完成第 1 项，不能按空项目重新访谈。不得覆盖本地已有文件或不同的 remote。
   - **待新建仓库**：若工作区为空且确认尚无目标远端，主动提出“需求确认后由协调者创建”，不要求用户先手工建仓库。有本地内容但无远端时也沿用此分支。进入需求确认前明确目标归属、仓库名、可见性及创建授权，已有决定直接继承，只问未决项；未获公开授权不得设为 public。此时记录 `待需求确认后创建`，目标名称不是已存在的仓库，不编造实际 URL 或声称建库完成。

**进入需求确认的条件**：第 1 项已完成，且第 2 项为“已有远端已核实”或“待新建计划及授权已明确”。后者无需先创建仓库；不得把“远端必须已经存在”设为门槛，造成需求确认与建库互相等待。向用户简短告知查到的事实和远端去向即可，不要求对这份事实摘要回复确认。

缺文件、缺配置时进入初始化准备，**不得只列缺项就结束，也不得要求用户另开一次 setup 才继续**；以下实际写入遵循已获授权，新建远端按需求确认后的阶段执行：
1. 沿用项目已有配置路径；没有时用 `templates/project-config.md` 生成 `docs/agents/orchestration.md` 草案，自动填入已核实值，只问未决选择。默认并发 1、交付 PR 不自动合并、通知在当前对话；不为可选机器人、真实数据快照或 `orca.yaml` 缺失阻断普通任务。
2. 一次说明本次需要的动作及范围：本地配置写入、Git 初始化/首次提交/remote、必要的 GitHub 仓库创建（归属、名称、可见性）、Orca 项目注册、GitHub 建票/评论/状态标签及指派同步/完成后关票/推送开 PR、是否允许合并、评审间保留开发终端。复用已有明确授权，不能把初始化调用本身视为无限授权。缺凭据只指引用户安全登录，不在聊天或配置里索要/保存 Token。
3. 获得必要授权后，由协调者写最小配置及 tracker 操作约定，补充现有 AGENTS.md（无则创建，只写已知边界与配置链接，不覆盖其他项目指引）。已有 CLAUDE.md 等指引继续遵守，不另造矛盾规则。可以参考现有 setup 的 GitHub 模板，但不强行安装它的 triage/领域文档体系。配置不得含秘密、未替换占位符或编造测试命令。
4. 逐项执行当前阶段实际需要的初始化并验证。沿用前置检查已确定的远端去向，不重问使用哪个仓库；待新建远端留到需求确认后，不阻断已满足前置条件的 html-plan。已有 Git 提交、remote、项目注册不重复做；配置 remote 仅在授权范围内执行，不覆盖不同的已有 remote。Orca 注册先读 `orca-cli` 和当前帮助，保存实际 repo 选择器；worker 必须能读取本套件及自包含任务说明。未安装工具或登录受阻时给出具体恢复动作，得到处理结果后从此处续接，不替用户改全局身份、跳 hook 或扩大权限。
5. 保存已完成和待需求确认后执行的初始化事项及原始需求指向；两项前置通过后**自动进入需求确认**，需求确认后继续剩余初始化与原请求，不要求用户再次输入 `/orca-issue-orchestration`。只有用户拒绝必要授权、缺不可替代输入或实际工具/权限失败无法解决时暂停，明确下一步；不因此转为协调者自己开发。

## 需求确认：html-plan

先核对上文两项前置检查已完成，再检查目标与基准、预期行为、范围/排除项、可执行验收、权限/隐私和未决事项，复用探查所得事实与既有决定，不把已有仓库信息重新包装为需求问题。讨论稿不等于实施授权，但其中已核实事实不需重新确认。已确认且未变的需求跳过重复访谈，落实远端仓库与剩余初始化后进入拆票阶段；这些准备已完成则直接拆票。

- **默认 html-plan**：调用共享 `html-plan`，依据已有证据提出方案，仅就真实待决项询问。每轮只问前置条件已明确的独立问题，依赖未知答案的问题留到下一轮。停止标准是当前任务的范围、验收和阻断性决策明确，不做穷尽式访谈。
- **wayfinder 仅显式启用**：只有用户明文要求使用 wayfinder（如 `/wayfinder`）才进入 Map / 决策票流程；任务复杂、文档不齐不构成自动启用许可。沿用每 session 一张 HITL 票的限制，research 例外不变；HTML 批量提问只在当前票内，不跨票结算。
- **中文需求页面**：每页 0–5 个真实待决问题；0 个且尚未整体确认时展示需求摘要供确认，已确认且未变则不再生成确认页面，1 个时只问这一题，不凑数量。简单追问可直接聊天，不额外调用其他访谈 Skill。页面是待讨论方案，不为填满布局虚构代码位置或已确认规则。用户点击 Respond（汇总答复）、Copy response（复制答复），手动粘贴 Markdown 回来；无自动回写服务，不自动公开发布。
- **本地澄清记录**：沿用项目已约定位置；没有时用 `.orchestration/clarifications/<clarification-id>/`，在写入前确保 Git 忽略。保存每轮页面/packed HTML、稳定问题 ID、答案原文与解释、未决项、关联 SPEC / Issue 的版本和用户确认记录。澄清不调用 `S init`，不为此创建开发 Run。页面标题携带澄清 ID 与轮次，使 Respond 标题可追溯；每轮用新文件，不覆盖旧答复。校验答复与页面版本的对应关系，过期或含糊答复先澄清。
- **答题不自动等于批准，明确批准不重复索取**：推荐默认、未打开问题、部分答复和沉默都不是整体确认。用户明确回复“全部采用推荐项”可按其明确范围记作决定；否则保留未答项。先核对用户原话及确认记录是否已明确批准当前需求的范围、边界与验收；只有尚未整体确认或无法确定所指内容时，才汇总并请求确认。用户可在同一回复中完成选择、确认方案并要求启动，无需再按指定句式回复。仅整理摘要、保存快照或赋予 V1 等版本号不构成需求变更，不能以“最终确认摘要”为由重新索取批准；实质更改需求后只重新确认受影响内容。
- **已确认并要求启动 → 继续执行，不追加确认轮**：若用户已明确批准当前需求并要求启动（如“按上述选择开始”“确认，直接推进”），将原话与对应需求快照、动作授权范围一并记录，直接继续必要初始化、拆票、建票和派发前检查；满足前置条件后实际派发，不停在“请回复确认 V1，之后我会启动”。在已向用户说明的动作范围内识别并复用其明确启动授权，不要求逐项重复授权；单纯需求确认或含糊的“开始”不自动授予未说明的远端写入、合并、真实数据操作或权限扩大。确有缺失授权或阻断性决策时，只说明具体缺项并询问该项，不重问整份需求；配置/文档尚未落盘等已授权的准备工作由协调者继续完成，不作为二次确认理由。
- **确认后落实远端及初始化，再拆票，不直接实现**：沿用既有 SPEC / Issue 写回决策与确认；没有文档位置时在初始化草案中给出最小落点供确认。保存确认版本/快照和验收依据，不让可变文档悄悄改变任务。GitHub 写操作须处于授权范围；wayfinder 决策票不是实现票，用户决策不能由 Agent 代答。配置仍缺项就回到初始化补齐，不因需求确认而豁免。所有派发条件齐全前不创建开发 Run、不派 worker。

## 需求确认后：落实远端仓库与剩余初始化

需求已确认后，检查前置阶段记录的远端状态：已有仓库直接复用；`待需求确认后创建` 则由协调者立即执行已授权的新建计划，不把建库交回用户，不再询问“是否现在创建”。若用户只批准需求但明确要求暂停执行，则保留计划，不越过暂停指令。

1. 复用已明确的归属、名称、可见性与创建授权；执行前再次只读查询目标，避免重复创建。查到同名仓库时核对是否为本项目已有结果；无法确定则停在该冲突，不擅自接管、改名或更改可见性。查询失败不能据此认定不存在。
2. 先读 `gh repo create --help`，按已授权参数创建；随后用 `gh repo view` 核对真实 `owner/name`、URL 与可见性并保存回执。超时或结果未知时先查询对账，不盲目重建。失败时记录具体错误并从本阶段恢复，不重新确认未变的需求。
3. 在授权范围内完成本地 Git 初始化、首次提交、remote 配置及必要推送；这些动作与建库授权分别核对，不能因允许建库就隐式使用 `--push` 或提交全部工作区文件。已有不同 remote 不覆盖，已有提交不重复初始化。继续核实 Orca 注册、worker 文档可达性及其他派发前置。
4. 更新编排配置中的真实远端信息与初始化结果，自动继续拆票建票；远端尚未实际创建或核实成功时，不执行 GitHub 建票、不创建开发 Run、不派 worker。缺权限只询问具体缺项，不索取整份需求的第二次批准。

## 已确认需求 → GitHub 实现 Issue

这是协调者必须执行的阶段，不能把“还没有 Issue”直接作为结束理由，也不能以本地任务列表或普通子代理任务替代 GitHub Issue。

1. 将确认版需求拆成可独立验收的纵向切片；每票给出目标、范围与禁区、确认版 SPEC 引用、验收行为/命令、依赖和必要用户节点。使用 `templates/issue.md`，避免仅按文件拆分或构造假依赖。先查已有 Issue，复用同一任务的票据，不重复建票；已有完整拆分不重做。
2. 展示简短拆分及依赖，收集尚未授予的建票、评论和派发授权。已批准的目标内机械拆分无需逐票重复确认；新增范围/产品取舍必须回到需求确认。需求确认不自动授予任何远端写入权限。
3. 建票前先创建或复用本任务的范围标签 `<task-name>`（简洁英文小写 kebab-case，如 `dynamic-models-csrf`）：先查同名标签及所属任务，仅确认是本任务的恢复才复用，其他任务同名不能混用；不存在则按已授权范围创建（统一紫色 `#5319e7`，description 写任务全名与开始日期）。按 tracker 约定用 `gh issue create --repo "<owner/name>" --title "<标题>" --body-file "<正文文件>" --label "<本任务标签>"` 建票，每张票都带这个任务标签，立即保存真实编号与 URL。标题统一为 `#<真实编号> [类型] <主题>`：建票时先用不含编号的标题，拿到返回编号后立即执行 `gh issue edit <n> --title "#<n> [类型] <主题>"` 回填并回读，编号必须与实际票号一致；复用已有票时，标题没有编号的同样回填。先创建全部票，再用 `gh issue edit --repo <owner/name> <n> --body-file <更新正文>` 写真实 `Blocked by: #n`；不把临时编号当 GitHub 编号。有原生依赖则按 tracker 约定同步。请求超时先查询核对已创建结果，不盲目重建。
4. 需要用户验收/决策的独立节点先建票，只加任务标签，不预打 `needs-user`。只有依赖全部满足、成为当前可执行前沿时才加 `needs-user`（仍阻塞下游或交付时同时加 `gate`），assign 给已核实的用户账号，并发一条以“需要你处理”开头的评论说明操作与回复方式；被阻塞的用户节点保持无标签。需要创建标签时先确认在授权范围。代码依赖在 PR 实际合并后满足；用户节点在对应版本明确通过后满足，关闭/取消本身不是通过。
5. 重新读取票据核对范围、验收、真实依赖和授权，保存票号与确认版本映射。此时才按命令参考执行 `TW start`：任务级托管绑定仓库与任务标签，先固定订阅边界，再对账全部当前票据和评论，确认对账并挂 `TW wait` 通知桥。安装、调用 Skill 和建票之前不提前启动；没有开发 Run 时用持久建票记录目录，不为监听虚构 Run。系统托管权限应处于授权范围，失败明确阻断。依赖无环、监听就绪且可执行票明确后，直接继续创建/恢复 Run 并派发，不再让用户手动启动。若只授权规划/建票则报告已建票及待授权派发，不宣称开发已启动。
6. 后续根据用户反馈追加票或纳入既有票，先 `TW scope begin --op-id <稳定操作ID>`，再创建 Issue、加同一任务标签并核验，最后 `TW scope end --op-id <同一ID>`；请求结果未知先对账，保留保护标记，不按超时自动清除。任务已停止时先恢复 `TW start` 再追加。标签关闭后不摘除；不能只核对首次保存的票单就停止 watcher。

## 派发前检查（缺项回到上述阶段补齐）

1. 需求已梳理完（如需求问题已解决、SPEC 已定稿）。规则确认是需求阶段的事，不在开发中设节点。
2. 实现任务已建成 GitHub Issue，每个写明验收条件和 `Blocked by: #n`。
3. 用户验收节点已建成独立 Issue；只有当前依赖已满足、确实在等用户的节点才加 `needs-user`，仍阻塞下游或交付时再加 `gate`。凡是需要用户反馈的事项（包括清理 issue 里要用户拍板的条目、开发中冒出的取舍问题），一律开独立用户节点票，在其成为当前前沿后加 `needs-user`、assign 给用户，并发一条以「需要你处理」开头的评论，写明选项和用户回复后协调者会做什么；只在对话里问不算。被其他票阻塞的节点先不加标签，避免标签视图把所有未完成票都显示成“等用户处理”。节点类型：数据确认（需要用户判断当标准）、不可逆 / 对外动作（改真实数据、扩大权限、真实投递）、体验验收（用户天天要用的界面）、最终验收（上线前）。
4. 本任务所有票都带同一个专属 `<task-name>` 标签，且任务 watcher 已启动、初始对账完成、通知桥已挂载；开发中新增的补票、纳入范围的既有票使用 scope 保护后加同一标签。
