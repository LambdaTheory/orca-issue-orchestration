# Orca Issue 编排

调用者是协调者：查证事实、确认需求、建票、派发、收取报告和验收；可以写编排配置、需求文档、票据和状态、运行验收，不写业务实现、业务测试或修复代码，不替 worker 解决代码冲突。开发与修复必须通过 Orca 受监督 worker；普通子代理不替代实施。Orca 不可用时恢复原流程，不改为自己实现。

## 开工与按需阅读

先读当前 `orca skills get orchestration` 和项目指引、编排配置、SPEC。确定项目路径后立即执行 `C start` 记录本次 skill 启动时间，再继续探查。已有事实、确认、授权及 Run/Dispatch 直接复用；配置缺项由协调者查证并补齐，只问真正待决项，不要求用户另开初始化任务。

本入口给出执行顺序。下列文件保留细节，**进入对应阶段时只读相关小节；已读且未变的内容不重复加载，不一次读完全部参考文件**。

| 当前事项 | 读取内容 |
|---|---|
| 首次探查、初始化、需求确认、建票或缺少派发条件 | [准备工作](references/preparation.md) 的对应阶段 |
| 首次设置路径、执行状态/等待命令或派发 worker | [命令](references/commands.md)；只用当前平台的版本 |

## 统一位置与解释器

- **`ORCA_ISSUE_SKILL_DIR` → `SKILL_DIR`**：有显式覆盖就使用它；否则取本次实际加载的 `SKILL.md` 所在绝对目录。不要用当前工作目录猜安装位置，也不要固定为 `.agents/skills` 或 `skills`。
- **`ORCA_ISSUE_PYTHON` → `PY`**：指定实际 Python 3 命令或解释器路径；未指定时 Windows 用 `python`，macOS / Linux 用 `python3`。调用始终带 `-X utf8`，路径加引号。
- **`REPO`**：正在开发的项目本地绝对路径，不是 GitHub `owner/name`，也不一定是 skill 安装目录。**`RUN_ID`** 使用已有 Run 或创建回执的真实 ID。
- 所有脚本都从 `SKILL_DIR/scripts/` 调用，模板从 `SKILL_DIR/templates/` 读取。worker 任务说明写入实际路径，不假定它继承协调者的 Shell 变量。
- 使用 `implement` 时先核实可达路径；同套件通常为 `SKILL_DIR` 同级的 `implement/SKILL.md`。在开发模板中填入该绝对路径，不要求目标仓库存在 `.agents/`。

## 执行主线

1. **探查后再确认需求。** 阅读现有代码、文档与决定，核实已有远端或明确待新建计划；无需先建远端。已有确认且范围未变就直接继续。需要澄清时用 html-plan，每页 0–5 个真实独立问题，不凑数量。推荐默认不自动等于批准；用户已经明确确认则不再次索取批准。
2. **确认后完成初始化与建票。** 复用授权，执行仍缺的初始化，保存真实仓库、Issue、依赖和验收依据；为本次任务创建或复用 `<task-name>` 范围标签并应用到所有票；查询失败不等于不存在，请求结果未知先核对，不重复创建。派发条件见准备工作。
3. **建票后拆守护、启动监听，再绑定 Run 并派发。** 安装 Skill、调用命令和分析需求期间不启动 watcher。首批 Issue 创建并加上本任务专属标签后，先按[守护终端](references/guard.md)拆出守护终端，再按命令参考启动任务级系统托管，完成初始 GitHub 对账并挂本地通知桥；托管未就绪则报告阻断，不假称正在监听。守护只处理权限确认弹窗和停摆提示，按白名单放行、越界挂起，不代替需求决定，也不重派任务。任务范围以仓库和任务标签动态查询，不固定为首批票号；后续新增票先登记范围变更保护，创建/打标核验成功后解除。恢复现有尝试；需要新任务才创建。只根据权威回执记录 Task、Dispatch、Agent、worktree 和实际 worker 类型。ready 且输入已接受才记为已派发；未知结果先对账，不重复派发，也不把打开终端当开始开发。
4. **开发 → 一次独立评审 → 必要修复。** 开发者自查并完成必要验证；独立评审同时核对需求与正确性，不再叠加完整 code-review 或两路子评审。有必须修改项才开修复轮，修复后只复查增量与回归点。意见、结果与测试证据绑定实际 SHA。
5. **验收后按授权交付。** 复用同 SHA、环境与范围未变的有效测试结果；没有新改动、新失败或未解决疑点就不扩大验证。遵守已明确的测试约定，不默认全量测试/build。默认交付 PR，不自动合并；依赖任务按项目既有合并规则解锁。
6. **同步状态并收口。** 本地状态不会自动更新 GitHub；收到用户答复、阶段变化或合并结果时，同轮同步实际可见状态。标签只反映当前：`needs-user` 仅标依赖已满足且在等用户的节点，`gate` 仅标当前仍阻塞下游或交付的用户节点；被阻塞或已关闭的票不带这两个标签。任务标签 `<task-name>` 建票即加、关闭不摘除，用于圈定本次任务范围。明确完成与仍待合并/验收的事项，记录短检查点，按既有生命周期释放资源；停止守护终端与 `TW stop` 同轮完成，未处理的 hold 先说明再关；清理问题与非阻断建议不扩成新的实现任务。收口完成后执行 `S finish --reason completed|paused|cancelled`，生成 `timing.md` 并报告总历时、有效工作与等待；随后把该章节回填到最后合并或交付的 PR（`PT`），没有 PR 时保留 `timing.md` 并在最终报告说明。

## 协调循环

- 每轮 `S show` 只读当前摘要；单票用 `show --issue <n>`，完整历史按需用 `show --full`。只有状态变化才写回，不追加重复的“仍在等待”。
- 每小时向当前终端回报一次进展：用 `RP --wait <间隔秒>` 作为宿主后台计时，唤醒后原样输出小时报并重新挂起；只报告 `state.json` 的当前事实，不改阶段、不派发、不据此判断 worker 生死。任务结束后停止计时，只剩用户待答仍保留。
- 默认同一模型服务只安排一个执行/评审 Agent，开发、修复和原生子代理共用额度；已有明确并发约定优先。
- 开发、修复、评审使用 Orca 事件等待，并由同一个 `orch_wait.py` 低频只读检查 worker 健康；空超时和存活心跳不唤醒模型，发现异常才交给协调者，不让模型轮询倒计时。默认检查间隔 60 秒、done/idle 未结算宽限 120 秒、无可见进展阈值 900 秒，调用方式与边界见命令参考。GitHub watcher 由任务级系统托管，生命周期独立于 worker 和一次性通知桥：当前任务标签下仍有未关闭 Issue 就保持监听，开发、评审、PR 已交付或长期用户等待都不能作为停止理由。每次恢复执行或准备等待前检查状态；仅任务期望状态仍为 running 且采集异常死亡时，优先通过原状态目录执行幂等启动恢复，再处理业务；用户主动暂停或已停止不自动恢复。只剩用户待答时停止无用的 worker 等待/健康检查，但保留 GitHub 监听。
- 收到批次先核对当前任务、处理消息并持久化，再按现有协议 ACK、续等。`kind=health_alert` 是本地检查提醒，不是 worker_done 或任务失败回执；先按恢复参考核实并记录处置，不能机械重挂、自动杀进程或重派。`guard_hold` 表示守护把某个授权挂起了：先读 hold 的 `tool`/`input`/`rule`，属于流程内就直接 `verdict <id> allow --reason`，不属于就保留给用户；`guard_unavailable` 先看 `guard.log`，再用原状态目录 `guard start` 幂等恢复。完成报告与用户答复的处理、关闭条件见操作细则；不得把等待超时或联系中断判成 worker 死亡。
- 临时 503/断流先对账并取回已有报告，按 Orca 指引在同一任务内最多自动重试 2 次；无变化的配置错误不反复重试。需要用户新决定才停，不重新询问已有事实和授权。

**实现交付与消息监听分别收口。** 已授权实现完成后不凭建议加任务，但当前任务标签下的 Issue 未全部关闭就继续监听，不把结束答复或通知桥退出当成结束采集。必须通过受控停止接口重新完整查询标签范围，核实全部 CLOSED、无新增票操作、对账/同步待办和未确认批次后，才停止并撤销本期系统任务。查询失败、范围未知或正在追加票都不能停止，不得为停机提前关票。用户明确暂停/取消用显式暂停入口并记授权；交接只交接通知桥和处理责任，不关闭采集器。系统托管保护进程恢复，但不能阻止同权限强制卸载，也不能自动恢复已结束的 Agent 会话。
